# Objects index

Generated by `task map` from the cards' frontmatter and first sentence. Do not edit.

## sources

- [Bitcoin source (`bitcoin.Source`)](sources/bitcoin-source.md) — A read-only Bitcoin wallet (source type `bitcoin`) built from an xpub/ypub/zpub, address, output descriptor or wallet file, scanned through an Esplora HTTP API. · verified
- [Brokerage source (`brokerage.Source`)](sources/brokerage-source.md) — Source type `brokerage`: a stock/ETF/fund account typed in by hand as tickers and share counts, plus cash; CryptKeeper never connects to the broker. · verified
- [Coinbase source (`sources.TypeCoinbase`, `coinbase.Source`)](sources/coinbase-source.md) — A read-only Coinbase account, authenticated with a view-only CDP API key (key name plus private key), whose balances come from two APIs reconciled by account id and whose activity comes from the v2 transaction list. · verified
- [HTTP client (`httpx.Client`)](sources/http-client.md) — The one HTTP client every networked source (not manual or brokerage), the price service and the ntfy notifier share: 20 s timeout, JSON helpers, a fixed user agent, retry with backoff, and a process-wide per-host request pacer. · verified
- [Kraken source (`sources.TypeKraken`, `kraken.Source`)](sources/kraken-source.md) — A read-only Kraken account over the private Spot REST API: balances from `Balance`, activity from `Ledgers`, signed with an API key and base64 secret (HMAC-SHA512). · verified
- [Manual source (`manual.Source`)](sources/manual-source.md) — Source type `manual`: holdings typed in by hand for coins held anywhere the app cannot read; priced like any other holding. · verified
- [Solana DeFi positions (`solana/defi` adapters)](sources/solana-defi.md) — The adapters that read a Solana wallet's Orca, Raydium and Jupiter positions and report the assets underneath as legs, which solana-source turns into tagged holdings. · verified
- [Solana source (`sources.TypeSolana`, `solana.Source`)](sources/solana-source.md) — A read-only Solana wallet: native SOL, every SPL token (Token and Token-2022), native stake accounts, an NFT count and the wallet's Jupiter limit-order vault, built from one public address; DeFi positions come from solana-defi. · verified
- [Source contract (`core.Source`, `core.WalletResult`, `core.Holding`)](sources/source-contract.md) — The small set of types every source type implements and returns; the aggregator and UI only ever see these, never a Coinbase or Esplora type. · verified
- [Source definition (`sources.Def`, `sources.Registry`)](sources/source-def.md) — A "source" (UI word: wallet) as the user configures it is a `sources.Def` row in `data/sources.yaml`; the `Registry` owns that file and turns each row into a live `core.Source` through a factory. · verified

## valuation

- [Price](valuation/price.md) — A USD spot price with optional 24h change (`core.Price`), resolved per asset key by `prices.Service`, which tries several upstream sources, caches in memory, and keeps a last-good copy in SQLite. · verified
- [Snapshot](valuation/snapshot.md) — `portfolio.Snapshot` is the fully priced state of every connected source (or of one portfolio after filtering), built by the `Aggregator`, held and refreshed by the `Refresher`, and fanned out by the SSE `Broker`. · verified
- [Value history](valuation/value-history.md) — Portfolio value over time: `portfolio.History` and its `history` table (amounts and prices per sample), plus the separate `price_history` table of daily USD closes served by `prices.Service`, plus the per-wallet on-demand chart backfill. · verified

## views

- [Alert rule](views/alert-rule.md) — A user-defined alert (`alerts.Rule`, stored in `data/alerts.yaml`) that the `Engine` evaluates after every refresh or new activity, delivering through ntfy and logging to `alert_log`. · verified
- [Portfolio view](views/portfolio-view.md) — A user's named portfolio (`portfolios.Portfolio`, stored in `data/portfolios.yaml`): a filter over wallets and assets, plus a watch list, that turns the full snapshot into one portfolio's snapshot. · verified

## ledger

- [Activity entry](ledger/activity-entry.md) — One transaction of one source: `core.Tx` (the UI and docs call it an "activity" entry), kept in the `activity` table by `activity.Store` and refreshed by `activity.Syncer`. · verified
- [CSV export](ledger/csv-export.md) — `internal/export`: four plain CSV downloads (holdings, portfolio history, profit and loss, activity) written for spreadsheets; the package is only formatting, the handlers choose the data. · verified
- [Koinly import](ledger/koinly-import.md) — `internal/tax/koinly` parses Koinly's CSV exports and builds the opening tax lots; the upload, map, accept or discard wizard (`/reports/koinly`) in `internal/server/koinly_handlers.go` runs it and closes the imported year. · verified
- [Manual cost basis](ledger/manual-cost-basis.md) — `internal/costbasis`, two halves: the live Coinbase/Kraken CSV parsers that turn exchange exports into activity, and the retired manual cost entries of `data/costbasis.yaml` (leftover: kept for backups and a one-time migration). The card is `live` for the parsers; treat everything marked *leftover* below as leftover. · verified
- [Tax lot](ledger/tax-lot.md) — The FIFO cost basis of `internal/tax`: per-wallet, per-asset lots (`tax.Lot`), the disposals and income they produce, the review issues, and the user's tax inputs in `data/tax.yaml` and closed years in `data/tax/<year>.yaml`. · verified
- [Tax report](ledger/tax-report.md) — The year report shared by every tax download and print page (`internal/tax/report`), and the filler that writes it onto the official IRS Form 8949 and Schedule D PDFs (`internal/tax/irs`). · verified

## storage

- [Backup file](storage/backup-file.md) — The one YAML file a user downloads to save everything they configured (package `internal/backup`, type `backup.File`), optionally with the whole database inside. · verified
- [Config](storage/config.md) — Server settings from `config.yaml` (never written by the app) plus secrets read from environment variables, loaded once at startup into `config.Config` (package `internal/config`). · verified
- [Database](storage/database.md) — The SQLite file `data/cryptkeeper.db` (package `internal/store`, type `store.DB`) holds all machine-written state; human-editable state lives in YAML instead (yaml-store). · verified
- [Secret key](storage/secret-key.md) — The one AES-256-GCM key (type `secrets.Box`, package `internal/secrets`) that seals exchange API secrets and saved API keys at rest and, when the user supplies the key, whole exports. · verified
- [YAML store](storage/yaml-store.md) — The human-editable files under `data/` (package `internal/yamlfile` is the shared read/write layer; each file has its own owning package and store type). · verified

## web

- [Demo fixtures](web/demo-fixtures.md) — `internal/demo` builds invented but internally consistent view models for every screen; `cmd/uipreview` serves them on :8790 (`task preview`) and `cmd/uipreview/genicons` renders the app icon. · verified
- [Page model](web/page-model.md) — The plain Go view models (`OverviewPage`, `SettingsPage`, `PortfoliosPage`, `WalletPage`, ...) and the display-decision helpers in package `web/templates` that sit between a handler and a `.templ` file. · verified
- [Server](web/server.md) — The HTTP layer of CryptKeeper: package `internal/server`, a chi router (`server.New`) over a `Deps` struct that `main.go` fills in `serve`. · verified
- [Static assets](web/static-assets.md) — Everything the browser fetches from `/static/`: design tokens, component CSS, the vendored Datastar bundle, the chart hover script, fonts, icons and the PWA manifest, all embedded in the binary by `web/static/embed.go`. · verified
- [Templ components](web/templ-components.md) — The `.templ` sources in `web/templates/`: the app shell (`layout.templ`), shared components (`components.templ`, `icons.templ`) and one file per page, plus the Datastar expression builders in `js.go`. · verified
